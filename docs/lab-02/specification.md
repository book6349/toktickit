# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a responsive Requester-facing TokTickIT MVP that lets a selected Development Requester create, find, inspect, and manage permitted IT-support-ticket attachments while enforcing requester ownership.

## 2. Stakeholder Request Interpretation

Lab 2 simulates the future logged-in Requester context with a seeded Requester selector. It is not authentication. The selected Requester owns the tickets shown and may create tickets, view owned details, add attachments, download active attachments, and soft-remove owned attachments.

## 3. Scope

### Included

- Active Development Requester selection and switching
- Create Ticket workflow
- PostgreSQL-backed Categories and Related Systems
- Backend-generated Ticket Number and Ticket Date
- Ticket validation and duplicate-submit prevention
- My Tickets search, filters, sorting, and pagination
- Owned read-only Ticket Detail
- Attachment upload, metadata, download, and soft removal
- Zen Green reusable UI and responsive behavior
- Unit, API, UI, responsive, visual, and E2E tests

### Excluded

- Real authentication, passwords, sessions, tokens, or roles
- IT Staff dashboard, assignment, or workflow
- Comments, Internal Notes, or Actions Taken
- Status changes after `NEW` (shown as `New` in the UI)
- Administrator or reference-data management

## 4. Functional Requirements

- FR-01: Show a Development Requester selector before ticket screens.
- FR-02: Load only active Requesters from PostgreSQL.
- FR-03: Show loading, empty, and safe failure states for selection.
- FR-04: Persist the selected Requester for the current browser session.
- FR-05: Show the selected Requester in the application shell.
- FR-06: Allow Change Requester and reload requester-scoped data.
- FR-07: Load active Categories and Related Systems from the API.
- FR-08: Create a Ticket with Category, Related System, Requested Priority, Summary, Description, and optional Attachments.
- FR-09: Display Requester as read-only and derive it from the selected context.
- FR-10: Generate Ticket Number and Ticket Date on the backend.
- FR-11: Validate ticket fields on both client and server.
- FR-12: Prevent duplicate submission while creation is in progress.
- FR-13: Preserve form values after an API failure.
- FR-14: Display the official Ticket Number after successful creation.
- FR-15: Enforce attachment type, size, and active-count limits.
- FR-16: List only tickets owned by the selected Requester.
- FR-17: Support ticket search, category/priority/status filters, sorting, and pagination.
- FR-18: Distinguish loading, empty, no-results, and failure states.
- FR-19: Display an owned Ticket Detail screen in read-only mode.
- FR-20: Reject direct access to another Requester’s Ticket or Attachment.
- FR-21: Allow adding permitted Attachments to an owned Ticket.
- FR-22: Allow downloading active Attachments only.
- FR-23: Soft-remove an owned Attachment with a required reason.
- FR-24: Preserve removed Attachment metadata while blocking download and preview.

## 5. Business Rules

- BR-01: Ticket Number is generated by the backend and is unique.
- BR-02: Every new Ticket starts with API/database status `NEW`, displayed as `New` in the UI.
- BR-03: Ticket Date is generated by the backend.
- BR-04: The selected Development Requester is a testing context, not authentication.
- BR-05: Only active Requesters may be selected.
- BR-06: Changing Requester clears or reloads all requester-scoped data.
- BR-07: A Ticket belongs to exactly one Requester.
- BR-08: A Requester may retrieve only their own Tickets and Attachments.
- BR-09: Required text is trimmed before validation and storage.
- BR-10: Summary is required and must contain 5–150 characters after trimming.
- BR-11: Description is required and must contain 10–5,000 characters after trimming.
- BR-12: Requested Priority is one of `LOW`, `MEDIUM`, or `HIGH`.
- BR-13: Category and Related System must be active records.
- BR-14: The Create action is disabled while submission is in progress.
- BR-15: A failed submission does not erase entered values.
- BR-16: Allowed Attachment types are JPG/JPEG, PNG, WEBP, and PDF.
- BR-17: Each Attachment is limited to 5 MB.
- BR-18: A Ticket may have at most five active Attachments.
- BR-19: Stored filenames are generated safely and are not taken directly from user filenames.
- BR-20: Original filename, MIME type, byte size, storage key, and upload time are retained as metadata.
- BR-21: Removal requires an explicit confirmation and a reason of 5–250 characters.
- BR-22: Removal sets soft-removal metadata and does not delete the database record.
- BR-23: Removed Attachments cannot be previewed or downloaded.
- BR-24: Invalid list parameters return a safe client error.
- BR-25: Pagination is one-based and uses documented allowed page sizes.
- BR-26: Search covers Summary and Description case-insensitively.
- BR-27: Empty and no-results states are presented differently.
- BR-28: No Lab 3 authentication behavior is implied by the selector.

## 6. UI Specification Summary

The UI uses the Zen Green tokens:

- Primary: `#006B3C`
- Secondary: `#0B7A46`
- Pale: `#EAF6EF`
- Background: `#F5F7F6`

The shell contains TokTickIT identity, My Tickets, Create Ticket, active Requester display, Change Requester, and responsive mobile navigation.

Required states include selection loading/empty/error, form initial/loading/validation/submitting/success/failure, list loading/empty/no-results/error, and attachment active/uploading/invalid/removed/unavailable.

Desktop uses a centered multi-column layout at 992px and above. Tablet uses practical two-column layout from 768–991px. Mobile stacks controls below 768px with no horizontal scrolling.

## 7. Data Changes

- `RequesterUser`: id, name, email, isActive, createdAt.
- `Category`: id, unique name, isActive, createdAt.
- `RelatedSystem`: id, unique name, isActive, createdAt.
- `Ticket`: id, unique ticketNumber, ticketDate, requesterId, categoryId, relatedSystemId, requestedPriority, status, summary, description, createdAt, updatedAt.
- `Attachment`: id, ticketId, originalFilename, storageKey, mimeType, sizeBytes, uploadedAt, removedAt, removalReason, removedByRequesterId. The API field `isRemoved` is derived from `removedAt != null` and is not stored separately.

Relationships:

- RequesterUser 1-to-many Ticket
- Ticket 1-to-many Attachment
- Category 1-to-many Ticket
- RelatedSystem 1-to-many Ticket

Indexes cover requester ownership, ticket dates, category, priority, status, and ticket search/list access.

Seed data must be idempotent and include four required Categories, at least six Related Systems, four active Requesters, and one inactive Requester.

## 8. API Contract Summary

- `GET /api/requesters/active`
- `GET /api/categories`
- `GET /api/related-systems`
- `POST /api/tickets`
- `GET /api/tickets`
- `GET /api/tickets/:ticketId`
- `POST /api/tickets/:ticketId/attachments`
- `GET /api/tickets/:ticketId/attachments`
- `GET /api/attachments/:attachmentId/download`
- `DELETE /api/attachments/:attachmentId`

Requester-scoped operations use the selected simulated Requester context through the `X-Requester-Id` header. Successful retrievals use `200`, creation uses `201`, invalid input uses `400`, missing or unauthorized resources use a documented safe response, unsupported files and oversized files use documented client errors, and unexpected failures use `500` without stack traces.

## 9. Acceptance Criteria

- AC-01: An active Requester can be selected and continued into the application.
- AC-02: Inactive Requesters never appear in the selector.
- AC-03: Selector loading, empty, and failure states are visible and usable.
- AC-04: The selected Requester is visible in the shell and can be changed.
- AC-05: Valid ticket data creates exactly one persisted Ticket.
- AC-06: The response and success UI display the backend-generated Ticket Number.
- AC-07: Invalid fields show field-level messages and do not call the API.
- AC-08: Submit controls are busy and disabled during creation.
- AC-09: API failure preserves all entered values.
- AC-10: Valid attachments are accepted and invalid attachments are rejected with reasons.
- AC-11: A Requester sees only their own Tickets.
- AC-12: Search, filters, sorting, and pagination change the result set correctly.
- AC-13: Empty, no-results, loading, and failure states are distinct.
- AC-14: An owned Ticket opens in read-only mode.
- AC-15: Cross-Requester Ticket access is rejected.
- AC-16: An owned Ticket accepts a permitted new Attachment.
- AC-17: Active Attachments can be downloaded.
- AC-18: Soft removal requires a reason and preserves metadata.
- AC-19: Removed Attachments cannot be downloaded or previewed.
- AC-20: Desktop, tablet, and mobile layouts have no clipping, overlap, or horizontal overflow.
- AC-21: Labels, focus indicators, required markers, and validation messages are accessible.
- AC-22: Every acceptance criterion maps to at least one planned automated test.

## 11. Assumptions and Decisions

- The selected Requester is stored only for the current browser session.
- The selector is intentionally not secure authentication.
- Ticket Number uses a backend-generated `TT-YYYYMMDD-XXXXXX` format with uniqueness retry.
- Removed Attachment metadata remains visible to the owning Requester.
- Cross-Requester resources are hidden with a safe missing-resource response.
- Requester-scoped API calls use `X-Requester-Id`; this is a testing context and not authentication.
- Initial and additional attachment batches use all-or-nothing validation and storage cleanup on failure.
